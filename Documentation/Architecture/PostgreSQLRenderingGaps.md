# PostgreSQL rendering gaps

This note records what SwiftQL cannot express for PostgreSQL after the
rendering seam landed. It is the output of the
[PostgreSQL rendering spike](https://github.com/lukevanin/swiftql/milestone/35)
and the input to the
[PostgreSQL vertical slice #137](https://github.com/lukevanin/swiftql/issues/137)
and to
[typed DDL #139](https://github.com/lukevanin/swiftql/issues/139).

SwiftQL **does not support PostgreSQL**. `XLPostgreSQLDialect` renders SQL and
has no driver, no transport, and no connection type. Nothing here is a
supported surface, and the conformance inventory records no PostgreSQL claim.

The golden rendering is `Conformance/PostgreSQL/GOLDEN.sql`, generated by
`PostgreSQLGoldenRenderingTests`.

## What the spike proved

The dialect is the rendering seam. Every case in the golden file renders
through the same expression nodes, the same builder, and the same encoder as
SQLite. Only the dialect differs.

| Concern | SQLite | PostgreSQL |
| --- | --- | --- |
| Equality | `==` | `=` |
| Null-safe equality | `IS` | `IS NOT DISTINCT FROM` |
| Null test | `ISNULL` | `IS NULL` |
| Conditional | `IIF(c, t, f)` | `CASE WHEN c THEN t ELSE f END` |
| Blob literal | `x'deadbeef'` | `'\xdeadbeef'` |
| Regex match | `REGEXP` plus a registered function | `~`, nothing registered |
| Placeholders | `:name` and `?5` | `$1`, `$2`, `$3` |
| Collation | `COLLATE BINARY` | `COLLATE "C"` |

A statement written with named parameters renders positionally for
PostgreSQL and reports only `.indexedBindings`. The logical key stays named,
so application code still binds by name.

## Gaps

Each gap states what breaks, and who must close it.

### G1 — A recursive common table is not marked

**Severity: blocks correct SQL.**

PostgreSQL requires `WITH RECURSIVE` before a recursive common table.
SQLite accepts a plain `WITH`, so SwiftQL never records whether a common
table is recursive, and the builder always renders `XLCommonTablePrefix.with`.
`XLPostgreSQLVocabulary` can spell `WITH RECURSIVE`, but nothing asks it to.

A recursive query therefore renders SQL that PostgreSQL rejects.

**Closes in #137.** The common-table builder must carry whether the list is
recursive, which is a change to the statement model rather than to a dialect.

### G2 — No native types

**Severity: blocks a driver.**

`XLPostgreSQLValue` carries the five storage classes this proof needs.
`uuid`, `json`, `jsonb`, `timestamptz`, arrays, and ranges have no
representation. They were deliberately **not** routed through SQLite's storage
presets, because a `uuid` bound as SQLite `TEXT` is a different column type
with different comparison and index behaviour.

**Closes in #137**, together with the codec work that gives each native type
its own storage identifier.

### G3 — Named placeholders have no spelling

**Severity: latent.**

`XLPostgreSQLFormatter.namedBinding(_:)` cannot produce valid SQL, because
the extended query protocol has no named placeholder.
`XLPositionalPlaceholderAssigner` never yields one, so the method is
unreachable through the dialect's own assigner, and it renders `$name`, which
the server rejects at parse time rather than binding the wrong value.

**Closes in #137.** A driver should make the state unrepresentable rather than
relying on the assigner's discipline.

### G4 — An insert conflict algorithm is silently dropped

**Severity: changes meaning. A driver must refuse the statement.**

SQLite carries the algorithm in the opening keyword, `INSERT OR IGNORE INTO`.
PostgreSQL resolves a conflict with a trailing `ON CONFLICT` clause, which is
a different position in the grammar, so a vocabulary that only spells the
opening clause cannot express it.

`XLInsertTarget.insertOr` and `.replace` therefore render a plain
`INSERT INTO`. The SQL is legal and its meaning is wrong: it raises on
conflict instead of skipping or replacing the row. The golden file marks this
case with a `!!` warning.

**Closes in #137.** The insert statement must model the conflict clause as a
clause, not as part of the keyword. Until then a PostgreSQL driver must reject
any statement whose target is `.insertOr` or `.replace`.

### G5 — Two collations have no equivalent

**Severity: changes meaning. A driver must refuse the statement.**

`BINARY` maps to `"C"`, which also compares by byte value. `NOCASE` and
`RTRIM` have no PostgreSQL collation: case-insensitive comparison needs
`citext` or an ICU collation the database defines, and trailing-space folding
has no equivalent at all. Both currently render `"C"`, which compares
case-sensitively and keeps trailing spaces.

**Closes in #137.** `XLCollationName` should distinguish a sequence the
dialect guarantees from one it cannot provide, so rendering can fail rather
than quietly compare differently.

### G6 — Date modifiers are a different shape

**Severity: blocks correct SQL.**

SQLite applies modifiers as text arguments to `date(...)`:
`date('now', '+3 days', 'start of month')`. PostgreSQL uses interval
arithmetic and `date_trunc`, which is a different expression shape rather
than different text. `XLPostgreSQLVocabulary.spelling(for:)` returns text that
is not valid PostgreSQL on its own, and no golden case renders a date modifier
through this dialect.

**Closes in #137.** The date-function nodes need a dialect-chosen shape, the
way the conditional now has `XLConditionalForm`.

### G7 — No DDL

**Severity: blocks a catalog.**

The proof renders DML and expressions only. PostgreSQL column types,
`SERIAL` and identity columns, constraint syntax, and `CREATE INDEX` options
all differ from SQLite's and have no model.

**Closes in #139.** Typed DDL must be dialect-aware from the start rather
than modelled on SQLite and generalised later.

## What this changes for #137

The vertical slice is smaller than it was before the spike, because the
rendering seam and the placeholder model already exist. What remains is a
driver, native types, and the four statement-model changes above (G1, G4, G5,
G6) that no dialect can fix on its own.
