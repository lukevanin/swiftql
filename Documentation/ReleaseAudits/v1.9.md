# SwiftQL v1.9 release-readiness audit

The v1.9 line — "ergonomics, declared-query manifest emission, and evidence
refresh" — is a single-milestone minor release. Milestone
[v1.9](https://github.com/lukevanin/swiftql/milestone/34) holds the whole line,
so this record is produced at the `v1.9.0` release, as `RELEASING.md` requires
for every `vX.Y.0`. It is an evidence-backed record, not an implementation task.
It does not weaken, skip, or relabel a validation to reach a verdict.

Audited commit: `6cf4213c` on `version/1.9`. This commit is the merge of
[#769](https://github.com/lukevanin/swiftql/pull/769) and the head of the
branch. Every local result below comes from that exact commit. No
release-preparation commit exists yet. Thus the audited tree carries no dated
changelog heading, no release notes, and no version bump. "Release-preparation
actions" lists that work.

## Verdict

**Not ready for `v1.9.0` yet.** One release condition fails, and it is a
product condition, not a process condition.

Issue [#771](https://github.com/lukevanin/swiftql/issues/771) is open and stays
in the milestone. `RELEASING.md` step 1 requires the maintainer to merge every
retained issue and to close the milestone with no open issues. The live
milestone confirms the gap: `gh api repos/lukevanin/swiftql/milestones/34`
reports `state: open`, `open_issues: 1`, and `closed_issues: 33`. The one open
item is #771. The 33 closed items are the other 16 issues of the line and the
17 pull requests that the milestone also holds.

#771 is a source-compatibility defect. On Swift 6.3.2, a prefix `-`, `+`, or `~`
on a plain `Int` in a file that imports SwiftQL resolves to SwiftQL's generic
operator, not to the standard library operator. Ordinary user code then stops
compiling. `RELEASING.md` step 2 makes clean resolution on Swift 6.3 a
release-blocking cell, so the affected compiler is inside the supported matrix.
The maintainer must do one of two things before the tag: land the fix that #771
records, or move #771 out of the milestone with a written reason.

Everything else that this audit examined passes. All 16 other retained issues
are delivered by a merged pull request. The full first-party suite passes on the
audited tree: 1765 tests in 12 bundles, 0 failures. The conformance report is
current, and its totals agree with the documents that restate them. Each
supporting script that this audit ran returns exit 0, with one exception.

That exception is `check-strict-concurrency.sh`. It reports the same five
first-party `#SendableMetatypes` warnings that the v1.5, v1.6, v1.7, and v1.8
audits recorded. [#546](https://github.com/lukevanin/swiftql/issues/546) tracks
them in the v2.0 milestone. They are not a v1.9 regression, and no file that
v1.9 added contributes a warning. "The one local check that fails" gives the
detail.

One known risk remains outside the milestone.
[#772](https://github.com/lukevanin/swiftql/issues/772) records an intermittent
failure of the declared-query discovery fixture. "Known risks" describes it.

### The one open issue

| Issue | Pull request | Merge commit |
| --- | --- | --- |
| [#771](https://github.com/lukevanin/swiftql/issues/771) Keep Int negation for user code on Swift 6.3 | [#770](https://github.com/lukevanin/swiftql/pull/770) delivers a test workaround only | `ab44f355` |

#771 has no delivering pull request. PR #770 is titled "Fix the Swift 6.3 Linux
cell on version/1.9". It made the CI cell pass again. It did not repair the
library. The change annotates one line in `Tests/SQLTests/SQLInsertBatchTests.swift`
as `let magnitude: Int = -rawValue`. The annotation tells the compiler which
operator to choose, so the test target builds on Swift 6.3.2. User code gets no
such annotation.

The cause is recorded in the issue. `Int` conforms to `XLExpression`, at
`Sources/SwiftQL/Types/Intrinsic.swift:42`. SwiftQL declares generic prefix
operators over `any XLExpression<T>`, at
`Sources/SwiftQL/Operators/NumericOperators.swift:14`, `:18`, `:26`, and `:30`,
and at `Sources/SwiftQL/Operators/IntegerOperators.swift:14`. Swift 5.9.2 and
Swift 6.4 choose the standard library operator for a plain `Int`. Swift 6.3.2
chooses the SwiftQL operator. The issue records a Docker reproduction on
`swift:6.3.2-jammy` with a package that only does `import SwiftQL`.

Both operator declarations date from the first source commit. Therefore this
defect is not a v1.9 regression. It reaches every 1.x release on Swift 6.3. v1.9
is the release that found it, because
[#672](https://github.com/lukevanin/swiftql/issues/672) added the Swift 6.3.2
Linux cell to the compatibility matrix.

### Known risks

[#772](https://github.com/lukevanin/swiftql/issues/772) is open, has priority
P3, and carries no milestone. It records one intermittent failure of
`IntegrationTests/DeclaredQueryRegistryFixture/verify.sh`.

The failure happened in CI run 35020032020, on PR #767, attempt 1, in the
"Swift 6.0 / committed resolution" job. The runner killed the generator process
with signal 9 after the build completed. The captured log shows
`Build of product 'fixture-manifest' complete! (203.06s)`, and then
`Killed: 9`. The step and the script have no timeout, and the step builds
swift-syntax and SwiftQL again from scratch on every run.

The evidence says that the kill came from the runner, not from the code. PR #767
changed documentation only. The same step passed on #761's final commit, and
attempt 2 of the same job passed. The issue asks for three changes: separate the
build from the run, retry a signal-9 kill with no output once, and reduce the
cold build cost.

State this as a release risk, not as a defect in the release content. The step
blocks a release when it fails, and it can fail for a reason outside the code. A
maintainer who hits it during the release must re-run that job and record the
result.

### Source breaks that v1.9 carries

The `## [1.9.0] - Unreleased` changelog section opens with a `### Migration`
part. That part records six source breaks. Every break belongs to a delivered
issue.

1. **Declared queries generate new members** (#660). `@SQLQueries` adds a
   `preparedQueries` property and a nested `Context.PreparedQueries` type.
   `@SQLQuery` adds a peer `<name>PreparedQuery(...)` beside each executor. A
   member with the same name can stop compiling. The macro reports a collision
   inside its own extension. It cannot see a member outside the extension, so
   that case gives an "invalid redeclaration" error in generated code.
2. **Declared queries generate more members** (#659). `@SQLQueries` adds a
   `declaredQueries` property to the extended type and to its `Context`.
   `@SQLQuery` adds a `<name>DeclaredQuery()` method. A type that already
   declares one of these names gets a redeclaration error. The generated
   executors, their SQL, and their behaviour do not change.
3. **A `Data` value written into JSON fails before SQLite prepares the
   statement** (#671). The statement fails with the new case
   `XLSQLValueEncodingError.blobInJSONValue(valueType:function:)`. On 1.8.1
   SQLite reported `JSON cannot hold BLOB values`, or it read the bytes
   silently as a document. Pass the value through `minifiedJSONB()` to nest
   JSONB. A `switch` over `XLSQLValueEncodingError` with no `default` clause
   must handle the new case.
4. **A JSON mutation on a non-optional document has a non-optional result**
   (#664). Swift now infers `String` or `Data` where the call site gives no
   other type. Code that unwraps such a result twice must unwrap it once. The
   non-optional `jsonRemoving` and `jsonbRemoving` report the root path `$` with
   the new case `XLSQLValueEncodingError.jsonRootRemoval(function:)`.
5. **Build-validation manifest format version 2** (#658). New manifests are
   written as `format_version: 2`, and the reader accepts versions 1 and 2.
   `conformanceInventoryVersion`, `combinatorialManifestVersion`, and the two
   `valueTypeName` properties are now `String?`. Code that reads them must
   handle `nil`. `SQLiteBuildValidationManifestFormatVersion.current` is now
   `.v2`. `SQLiteBuildValidationManifestError` and
   `SQLiteBuildValidationPlanSuppressionError` each gain `unknownKey(path:)`.
6. **Unknown keys fail closed** (#658). The manifest and
   `swiftql-plan-analysis.json` reject a key that their schema does not define,
   at every level. A file that decoded on 1.8 because it had an extra key now
   fails. Remove or correct the key.

A seventh change is a behaviour change rather than a compile break. A Swift
`Bool` written into JSON is now a JSON boolean, not `1` or `0` (#671). Code that
reads such a member as a number must change. The changelog records it under
`### Changed`.

### Compatibility surface

The Swift 5.9 package floor does not change. The iOS 16 and macOS 13 platform
floors do not change.

OpenCombine is now a Linux-only dependency (#669). The `SwiftQL` target and the
test targets that import OpenCombine use
`condition: .when(platforms: [.linux])`. An Apple-platform build uses Combine and
links no OpenCombine module. The requirement changes from `exact: "0.14.0"` to
`from: "0.14.0"`. `Package.resolved` keeps the tested 0.14.0 pin.

SwiftQL 1.x supports GRDB 6 only (#667). The manifest range stays
`from: "6.29.3"`, which resolves to `6.29.3..<7.0.0`. `COMPATIBILITY.md` and the
README Install section now state that an application on GRDB 7 cannot resolve
SwiftQL 1.x. `Research/GRDB7Evaluation.md` records the build against GRDB 7.11.1
and the three breaks: the `CSQLite` product rename, the SQLite C module that
`import GRDB` no longer re-exports, and the `Sendable` closure and value
requirements. The `Sendable` findings go to the v2.0 `Row` decision, issue
[#685](https://github.com/lukevanin/swiftql/issues/685).

The compatibility matrix adds a Swift 6.3.2 Linux cell (#672). That cell found
the defect that #771 records.
