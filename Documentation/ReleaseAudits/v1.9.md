# SwiftQL v1.9 release-readiness audit

The v1.9 line — "ergonomics, declared-query manifest emission, and evidence
refresh" — is a single-milestone minor release. Milestone
[v1.9](https://github.com/lukevanin/swiftql/milestone/34) holds the whole line,
so this record is produced at the `v1.9.0` release, as `RELEASING.md` requires
for every `vX.Y.0`. It is an evidence-backed record, not an implementation task.
It does not weaken, skip, or relabel a validation to reach a verdict.

Audited commit: `7b48fdce` on `version/1.9`. This commit is the merge of
[#782](https://github.com/lukevanin/swiftql/pull/782) and the head of the
branch. Every local result below comes from that exact commit.

No release-preparation commit exists yet. The changelog heading still says
`## [1.9.0] - Unreleased`, and the six published-version claims still say
`1.8.1`. Those two facts belong together, and "Release-preparation actions"
explains why.

## Verdict

**Ready for `v1.9.0`**, subject to the human-gated release process in
`RELEASING.md`.

No product, documentation, compatibility, packaging, security, or performance
blocker remains. Every issue that the milestone retains is delivered by a merged
pull request. The full first-party suite passes on the audited commit
`7b48fdce`: **1781 tests in 12 bundles, 0 failures, exit 0.** The conformance
report is current, and its totals agree with every document that restates them.
The reader-facing documents state what the line shipped.

Issue [#771](https://github.com/lukevanin/swiftql/issues/771), which an earlier
revision of this document named as a blocker, is closed. PR
[#777](https://github.com/lukevanin/swiftql/pull/777) repaired it, and the
review proved the repair on the real Swift 6.3.2 compiler. "The Swift 6.3
operator defect, and its repair" records that evidence.

`gh api repos/lukevanin/swiftql/milestones/34` reports `open_issues: 0` and
`closed_issues: 35`. The 35 closed items are the 17 issues of the line and the
18 pull requests that the milestone also holds. The milestone itself still
reports `state: open`. The gate query in `RELEASING.md` step 1 tests the state
and the count together, so the maintainer must still close the milestone.

Issue [#772](https://github.com/lukevanin/swiftql/issues/772) is open and is no
longer in the milestone. That is deliberate, and `RELEASING.md` step 1 allows

The reason is recorded on the issue. The code shipped in the v1.9 line, in PR
[#782](https://github.com/lukevanin/swiftql/pull/782), which is the audited

One local check fails, and it is the same pre-existing failure that the v1.5,

first-party `#SendableMetatypes` warnings.

Three things belong to the release preparation itself rather than to this audit,

### The Swift 6.3 operator defect, and its repair

The defect was real, and it reached user code. `Int` and `Double` conform to
`XLExpression`. SwiftQL declares generic prefix `-`, `+`, and `~` over
`any XLExpression`. Swift 6.3 preferred the SwiftQL operator for a plain number.
In a file that imports SwiftQL, `let x = -someInt` then gave `x` an expression
type, and every later use of `x` as an `Int` failed to compile. Swift 5.9.2 and
Swift 6.4 always chose the standard library operator. The generic declarations
date from the first source commit, so the fault reaches user code on every 1.x
version under Swift 6.3, not only on 1.9.

The fix adds four exact-match overloads. `Sources/SwiftQL/Operators/NumericOperators.swift`
gains prefix `+` and `-` for `Int` at lines 49 and 53, and prefix `+` for
`Double` at line 57. `Sources/SwiftQL/Operators/IntegerOperators.swift` gains
prefix `~` for `Int` at line 26. `Double` deliberately gets no `-` overload.
Swift 6.3 already selects the standard library operator for `-someDouble`, and
an exact `-` overload for `Double` makes that call ambiguous.

The review proved each case with a consumer file that imports SwiftQL, compiled
by the real Swift 6.3.2 compiler:

| Consumer code | Before | After |
| --- | --- | --- |
| `let x = -v` (`Int`) | fail | pass |
| `let x = +v` (`Int`) | fail | pass |
| `let x = ~v` (`Int`) | fail | pass |
| `let x = -v` (`Double`) | pass | pass |
| `let x = +v` (`Double`) | fail | pass |

Three pieces of evidence hold the repair in place, rather than one convention.

1. **An out-of-package gate.**
   `scripts/ci/check-numeric-prefix-operator-type-safety.sh` compiles
   `Tests/CompileFail/NumericPrefixOperatorValid.swift` **outside** the package,
   against the built module. A test inside the package cannot prove this rule,
   because the defect appears in a client file. The fixture checks both
   directions: a plain `Int` or `Double` operand must keep its own type, and an
   `XLNamedBindingReference` operand must still give a SwiftQL expression,
   `-(-x)` and the optional forms included. With the overloads removed, the gate
   fails with four errors.
2. **A step in every cell of the `compatibility` job.** The gate runs as the
   step "Check numeric prefix operator type safety" in the `compatibility` job
   of `.github/workflows/swift.yml`. The step carries no `if:` condition, so
   every cell of that job runs it. The `swift-series` job, which produces the
   Apple clean-resolution cells, does not run the gate, so the Swift 6.1, 6.2,
   and 6.3 Apple cells do not carry it. The gate therefore runs in five of the
   eight release-blocking cells. The Swift 6.3 Linux cell is the only cell where
   the gate bites, because Swift 5.9.2 and Swift 6.4 select the standard library
   operator on their own.
3. **In-package tests.** `Tests/SQLTests/SQLNumericPrefixOperatorTests.swift` is
   new and holds 16 test functions for the same rule.

PR #777 also removed the annotation that PR #770 had added to
`Tests/SQLTests/SQLInsertBatchTests.swift`. The unannotated line now compiles,
which proves the defect is gone rather than hidden.

P3, and is **not** in the v1.9 milestone. It records an intermittent failure of
`IntegrationTests/DeclaredQueryRegistryFixture/verify.sh`.

Two of the six are on the pull request that carries this audit document. That
pull request changes one Markdown file and touches no code. A third is on the
documentation-currency pull request, which changes only Markdown and HTML. The
failure is therefore independent of the change under test.

The mechanism is recorded in the issue. The runner kills the generator process
with signal 9 after the build reports success. A captured log shows
`Build of product 'fixture-manifest' complete! (203.06s)`, and then `Killed: 9`.
Before #782 the script had no timeout, and it built swift-syntax and SwiftQL
again from scratch on every run.

**What #782 changed.** The script now:

- builds `fixture-manifest` and runs it as two steps, rather than as one
  `swift run`;
- caps SwiftPM at `--jobs 2`;
- gives the build 420 s and the run 180 s;
- retries one time on SIGKILL only, and never on a compiler error, a validation
  failure, or a timeout; and
- keeps and prints the log of each killed attempt, and writes a `::warning::`
  annotation, so each occurrence stays visible and countable.

A build failure now fails at once with its own message. Before, a failed build
in check 3 could look like the expected validation failure of that check.

The cap lowers the measured peak memory of a cold build from 3.42 GB at 14 jobs
to 1.38 GB at 2 jobs. **That measurement is local.** No measurement of the
runner exists, so the cap lowers the peak without proving that it stops the
kill.

**What the runs prove, and what they do not.** Two full matrix runs pass on the
#782 branch, run
[35086331450](https://github.com/lukevanin/swiftql/actions/runs/35086331450) on
`3af74597` and run
[35090394681](https://github.com/lukevanin/swiftql/actions/runs/35090394681) on
`65c453e9`. **No retry fired in either one**, so the runner killed nothing. The
runs therefore show that the step passes. They do not show that the retry works
on the runner, and two green runs do not clear a failure that appeared six times
in one day.

**The timing is noise, not a speed-up.** The fixture step took 148 s in run
35086331450 and 231 s in run 35090394681, for the same code in the same cell,
"Swift 6.0 / committed resolution". That 83 s spread is runner variance. It also
means the earlier 10 s gain measured on the clean cell is not a real speed-up.
State it plainly: the cost of `--jobs 2` is lost in the noise on these runners.

**The release effect is exact.** The tag-triggered release workflow requires all
eight compiler cells. A failure of this step fails the release run.
`RELEASING.md` allows "Re-run all jobs" for that case, so the release can
recover. Each occurrence costs a full matrix run. #782 lowers the chance and
makes each occurrence visible; it does not remove the risk.

### Source breaks that v1.9 carries

The `## [1.9.0] - Unreleased` changelog section opens with a `### Migration`
part. That part records six source breaks. Every break belongs to a delivered
issue.

1. **Declared queries generate new members** (#660). `@SQLQueries` adds a
   `preparedQueries` property and a nested `Context.PreparedQueries` type.
   `@SQLQuery` adds a peer `<name>PreparedQuery(...)` beside each executor. A
   member with the same name can stop compiling. The macro reports a collision
   inside its own extension. It cannot see a member outside the extension, so
   that case gives an "invalid redeclaration" error in generated code.
2. **Declared queries generate more members** (#659). `@SQLQueries` adds a
   `declaredQueries` property to the extended type and to its `Context`.
   `@SQLQuery` adds a `<name>DeclaredQuery()` method. A type that already
   declares one of these names gets a redeclaration error. The generated
   executors, their SQL, and their behaviour do not change.
3. **A `Data` value written into JSON fails before SQLite prepares the
   statement** (#671). The statement fails with the new case
   `XLSQLValueEncodingError.blobInJSONValue(valueType:function:)`. On 1.8.1
   SQLite reported `JSON cannot hold BLOB values`, or it read the bytes
   silently as a document. Pass the value through `minifiedJSONB()` to nest
   JSONB. A `switch` over `XLSQLValueEncodingError` with no `default` clause
   must handle the new case.
4. **A JSON mutation on a non-optional document has a non-optional result**
   (#664). Swift now infers `String` or `Data` where the call site gives no
   other type. Code that unwraps such a result twice must unwrap it once. The
   non-optional `jsonRemoving` and `jsonbRemoving` report the root path `$` with
   the new case `XLSQLValueEncodingError.jsonRootRemoval(function:)`.
5. **Build-validation manifest format version 2** (#658). New manifests are
   written as `format_version: 2`, and the reader accepts versions 1 and 2.
   `conformanceInventoryVersion`, `combinatorialManifestVersion`, and the two
   `valueTypeName` properties are now `String?`. Code that reads them must
   handle `nil`. `SQLiteBuildValidationManifestFormatVersion.current` is now
   `.v2`. `SQLiteBuildValidationManifestError` and
   `SQLiteBuildValidationPlanSuppressionError` each gain `unknownKey(path:)`.
6. **Unknown keys fail closed** (#658). The manifest and
   `swiftql-plan-analysis.json` reject a key that their schema does not define,
   at every level. A file that decoded on 1.8 because it had an extra key now
   fails. Remove or correct the key.

A seventh change is a behaviour change rather than a compile break. A Swift
`Bool` written into JSON is now a JSON boolean, not `1` or `0` (#671). Code that
reads such a member as a number must change. The changelog records it under
`### Changed`.

The #771 repair adds four public prefix operators. It is additive for a SwiftQL
expression operand, and it restores the standard library behaviour for a plain
number operand. It breaks no source that compiled before.

### Compatibility surface

The Swift 5.9 package floor does not change. The iOS 16 and macOS 13 platform
floors do not change.

OpenCombine is now a Linux-only dependency (#669). The `SwiftQL` target and the
test targets that import OpenCombine use
`condition: .when(platforms: [.linux])`. An Apple-platform build uses Combine and
links no OpenCombine module. The requirement changes from `exact: "0.14.0"` to
`from: "0.14.0"`. `Package.resolved` keeps the tested 0.14.0 pin.

SwiftQL 1.x supports GRDB 6 only (#667). The manifest range stays
`from: "6.29.3"`, which resolves to `6.29.3..<7.0.0`. `COMPATIBILITY.md`, the
README Install section, and the landing page now state that an application on
GRDB 7 cannot resolve SwiftQL 1.x. `Research/GRDB7Evaluation.md` records the
build against GRDB 7.11.1 and the three breaks: the `CSQLite` product rename,
the SQLite C module that `import GRDB` no longer re-exports, and the `Sendable`
closure and value requirements. The `Sendable` findings go to the v2.0 `Row`
decision, issue [#685](https://github.com/lukevanin/swiftql/issues/685).

The compatibility matrix adds a Swift 6.3.2 Linux cell (#672). That cell found
the defect that #771 records. The matrix also gains the numeric prefix operator
gate described above.

### Performance

v1.9 makes one performance claim, and issue #670 refreshed the evidence that
supports it.

**The claim: a batch insert is about 2.8 times faster than the per-row path.**
`GRDBDatabase.insert(contentsOf:)` renders the insert once, with a bound
parameter in place of each literal, prepares it once for the call, and binds
each row through an invocation packet. The per-row loop renders and prepares
once for each row.

On the Issue259 `transactional_write` workload, for one 100-row transaction,
`Benchmarks/Comparison/Issue259/README.md` records:

| Recording | Write path | SwiftQL median | Spread |
| --- | --- | ---: | ---: |
| 2026-09-15 before, round 1 (`35e78e53`) | per-row `sqlInsert(_:)` | 993.42 us | 5.1% |
| 2026-09-15 before, round 2 (`35e78e53`) | per-row `sqlInsert(_:)` | 1.00 ms | 4.0% |
| 2026-09-15 after, round 1 (`54abf673`) | `insert(contentsOf:)` | 363.98 us | 5.3% |
| 2026-09-15 after, round 2 (`54abf673`) | `insert(contentsOf:)` | 358.17 us | 4.5% |

The runs alternated between two clean revisions on one shared host. The two
"before" runs agree with the 2026-08-02 figure within 1%.

**Two limits are stated in the record rather than hidden.** First, the runs do
not establish an order between SwiftQL and GRDB on this workload. SwiftQL's
median is 7.6% and 7.5% below GRDB's in the two "after" runs, which is inside or
barely outside GRDB's own process spread. Second, the per-row figure measures
rendering, not preparation. The workload inserts the same batch every iteration,
so GRDB's statement cache already holds the 100 literal statements after warmup.
A workload with different values each time would add 100 preparations to the
per-row path only, and it was not measured.

**The baselines were re-recorded** (#670). The current baseline is revision
`ac7ac296`, recorded 2026-09-15 on a Mac16,8 with Apple M4 Pro, 14 cores and
24 GiB, macOS 26.6.2, Xcode 27.0, Swift 6.4, SQLite 3.51.0, and GRDB 6.29.3,
with SwiftPM's default Swift Build. No compile-time sample was rejected. The
one-minute load average stayed between 1.36 and 5.74 over 19 samples.

`BENCHMARKS.md` states plainly that these figures do not compare directly with
the historical ones, because the historical reports used Swift 6.3.2 with
SwiftPM's native build system. That is the honest position, and this audit does
not present a cross-toolchain trend.

The refreshed compile-time matrix produced the figure that motivates
[#773](https://github.com/lukevanin/swiftql/issues/773): a median clean debug
build of 236.64 s at 500 tables.

The evidence rules themselves also got stronger. The compile-time summarizer now
reads SwiftPM's own `complete!` duration from each raw log and rejects a sample
whose wall time is greater than twice that duration plus 2 s. On the checked-in
2026-08-02 logs it rejects three samples, in the 10-table SwiftQL clean cell and
the 10-query raw SQLite edit cell.

A second rule guards a different fault. The first 2026-09-15 recording attempt
found a harness defect: the 1-table by 10-query SwiftQL cell compiled 451 stale
tables that the 500-table cell had left behind, and it measured 207 s for a
build that takes about 2 s after the fix, which matches the August figure of
2.1 s. The wall-time rule could not catch that sample, because the build was
real: SwiftPM's own `complete!` duration was about 207 s as well. The harness now
checks that the consumer holds exactly its template and generated files, and
validation rejects a report whose generated file names disagree with the
declared scale.
