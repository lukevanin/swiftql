# SwiftQL v1.6 release-readiness audit

The v1.6 line — "SQLite JSON support on existing expression machinery" — is a
single-milestone minor release. Milestone
[v1.6](https://github.com/lukevanin/swiftql/milestone/17) holds the whole line,
so this record is produced at the `v1.6.0` release, as `RELEASING.md` requires
for every `vX.Y.0`. It is an evidence-backed record rather than an
implementation task, and it does not weaken, skip, or relabel any validation to
reach a verdict.

Audited commit: `8bc88334` on `version/1.6`, the merge of
[#606](https://github.com/lukevanin/swiftql/pull/606) and the last content
commit of the milestone. Every result below was produced against that exact
commit. This record is written on the release-preparation change that sits
directly on top of it, which adds only the documentation and release artifacts
listed under "Documentation currency"; the preparation change is re-validated
in its own pull request rather than re-audited here.

## Verdict

**Ready for `v1.6.0`**, subject to the human-gated release process in
`RELEASING.md`. No product, documentation, compatibility, packaging, security,
or performance blocker remains. Every issue retained in the milestone is
delivered by a merged pull request, the full first-party suite passes on the
audited tree, and the documentation, compatibility, and conformance records
agree with what the milestone shipped.

One local check fails, and it is the same pre-existing, already-tracked failure
the v1.5 audit recorded: `check-strict-concurrency.sh` reports five first-party
`#SendableMetatypes` warnings, tracked as
[#546](https://github.com/lukevanin/swiftql/issues/546) in the v2 milestone. It
is not a v1.6 regression; the warning set and the files are unchanged.

Three things belong to the release preparation itself rather than to this audit
and are listed under "Release-preparation actions": the milestone still holds
open issues and cannot close as `RELEASING.md` step 1 requires, the changelog
heading is still `Unreleased`, and the seven-cell compiler matrix has not yet
run on `main` with this content.

### The JSON surface, and what each part needs

SwiftQL renders the SQL whatever the engine is; the engine is what refuses. The
minimum versions are recorded per feature in the conformance inventory rather
than asserted in prose:

| Surface | Minimum SQLite |
| --- | ---: |
| JSON functions, `json_extract`, paths, aggregates | 3.9.0 |
| `->` and `->>` | 3.38.0 |
| `json_error_position` | 3.42.0 |
| JSONB, and `json_valid(X, F)` with flags | 3.45.0 |
| `json_pretty` | 3.46.0 |

The macOS cells in the supported matrix run SQLite 3.43.2. Everything above that
line is covered by execution tests that ask the connection what it defines and
skip with a message naming the runtime. Nothing above that line is added to the
combinatorial manifest, where a missing capability is a failure rather than a
skip. That split is deliberate and is recorded on each inventory feature's
deviations.

### Performance

Issue #353's two changes were each measured on their own against the state
before it, over six interleaved pairs on one machine, on a 16,143-row,
14-column fetch. The evidence lives in
`Benchmarks/Comparison/Issue353/README.md`.

| Change | Median | p95 | Range across pairs |
| --- | ---: | ---: | ---: |
| Constrained literal read (#605) | 72.38 ms → 43.88 ms | 74.67 ms → 45.32 ms | -38.4% to -40.0% |
| Hoisted column expressions (#606) | 42.74 ms → 30.63 ms | 44.08 ms → 31.32 ms | -26.9% to -30.1% |

The two compose to about 56%. The two baselines differ slightly because each
was measured in its own interleaved run, which is why the composition is stated
as a product of the two measured ratios rather than as a single end-to-end
number.

### Compatibility surface

Two source-level API differences across compiler cells now exist, both recorded
in `COMPATIBILITY.md`:

- `#row`'s two-to-six column shapes require Swift 6.1 or later (v1.5.4).
- `sql { ... }` as a subquery requires Swift 6.1 or later (#69, this release).
  The six `@_disfavoredOverload` overloads crash `swift-frontend` on the pinned
  Swift 5.9 and 6.0 cells when compiled with the rest of the package —
  reproduced in Docker and bisected to those declarations. This is the second
  attempt at #69; the first was reverted before v1.5.4 shipped for the same
  crash, so gating rather than reverting is the change of approach.

### Public API changes and deprecations

One deprecation and one narrow conformance change, both documented in the
changelog under `[1.6.0]`:

- `validJSON()` is deprecated in favour of `validJSONOrNull()` and
  `validJSONOrNull(flags:)`, because `json_valid(NULL)` returns SQL `NULL`
  rather than false and a non-optional `Bool` result cannot represent that. The
  old spelling still compiles and renders identical SQL, and will return an
  optional expression in SwiftQL 2.
- `XLRowReader` gains a second `staticColumn(_:alias:)` requirement constrained
  to `XLLiteral`. It has a default implementation forwarding to
  `column(_:alias:)`, so an out-of-package conformance keeps compiling. A
  conformance that overrode the unconstrained requirement specifically to give
  literal columns behaviour `column(_:alias:)` does not give will no longer see
  literal columns arrive there, and must implement the constrained requirement
  as well.

Everything else in the release is additive.

## Release-preparation actions

These belong to `RELEASING.md`'s own flow rather than to this audit, and are
listed so nothing is carried forward untracked.

1. **Close the eleven delivered issues and then the `v1.6` milestone.**
   `RELEASING.md` step 1 requires the live milestone to be closed with no open
   issues. Every issue's pull request merged into `version/1.6` rather than the
   default branch, and GitHub only auto-closes on the default branch, so each
   has to be closed by hand.
2. **Confirm the seven-cell `Swift compatibility` run and the `Documentation`
   run pass on `main`** with this content, per step 2. The `Documentation` run
   is also the only place the Hugo blog build and `check-blog-output.sh` are
   exercised for the new post.
3. **Run the safe `release-test/` tags** while the changelog still says
   `Unreleased`, per step 4.
4. **Date the changelog heading** — replace `## [1.6.0] - Unreleased` with
   `## [1.6.0] - YYYY-MM-DD` — and move the matching pin in
   `SQLDocumentationCatalogTests.testV13PublicDocumentsShareReleaseAndBoundaryContract`,
   which asserts the exact first release heading and carries a comment saying so.
5. **Re-verify immutable releases and the tag ruleset immediately before
   tagging**, per steps 5 and 6. Both were checked while preparing this record
   and both passed: `repos/lukevanin/swiftql/immutable-releases` reports
   `enabled: true`, and ruleset `19095830` "Protect v-prefixed release tags"
   matches its full expected record exactly — repository-owned, `tag` target,
   `active`, `current_user_can_bypass: never`, including `refs/tags/v*` with an
   empty exclude list, exactly the `deletion` and `update` rules, and no bypass
   actors. Neither check can be performed by the release workflow, and neither
   is satisfied by an HTTP 200 alone, so both are repeated at tag time.
6. **Announce the release.** v1.6.0 is a minor version, so it is announced
   rather than shipped silently: the "What's new in v1.6" blog post ships on the
   preparation commit, and the social and Swift Forums channels follow
   publication. Record the links in the release issue before closing it.
