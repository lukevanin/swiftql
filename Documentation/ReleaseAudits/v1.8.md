# SwiftQL v1.8 release-readiness audit

The v1.8 line — "query-plan analysis and index advice" — is a single-milestone
minor release. Milestone
[v1.8](https://github.com/lukevanin/swiftql/milestone/30) holds the whole line,
so this record is produced at the `v1.8.0` release, as `RELEASING.md` requires
for every `vX.Y.0`. It is an evidence-backed record rather than an
implementation task, and it does not weaken, skip, or relabel any validation to
reach a verdict.

Audited commit: `b3b91cc3` on `version/1.8.0`, the merge of
[#634](https://github.com/lukevanin/swiftql/pull/634) and the last content
commit of the milestone. Two commits sit above it and are described here rather
than audited as product work: a merge of `main` that brings the already-released
v1.7 line onto the base branch so the release merge can be made, and the
release-preparation change that carries the documentation and release artifacts
listed under "Documentation currency". Both are re-validated in their own pull
requests. Where a figure below was measured on the merged tree rather than on
`b3b91cc3` alone, it says so.

### What the analysis does, and what it costs

Everything the milestone adds is advisory by construction, and three separate
mechanisms hold that line rather than one convention:

1. **A separate artifact.** Plan records live in their own canonical JSON
   sidecar. `SQLiteBuildValidationReport` has no plan field, so the correctness
   report's schema, verdict semantics, and bytes cannot change when plans are
   captured. `testCapturingPlansLeavesTheCorrectnessReportByteIdentical` and
   `testCapturingPlansLeavesAFailingRunFailingAndNoWorse` assert byte identity
   on a passing run and a failing one.
2. **A separate severity type.** `SQLiteBuildValidationPlanDiagnosticSeverity`
   is its own type rather than a fourth `SQLiteBuildValidationVerdict` case, so
   no arrangement of it can reach the exit-status decision. As a verdict case,
   "never affects exit status" would have depended on every future `switch`
   keeping the convention.
3. **An unchanged exit rule.** `SQLiteBuildValidationValidatorCLIRunResult`
   still reads `report.overallVerdict` alone.
   `testAdvisoryDiagnosticsLeaveTheReportAndExitStatusAlone` and the plugin
   fixture's check 7 assert a build with findings still succeeds.

Cost is opt-in at every layer. Without `--plan-output` the validator captures
nothing and does no extra work; without `--verify-index-candidates` it copies
nothing; without `swiftql-plan-analysis.json` in its directory a target's plugin
invocation is unchanged. The fixture's check 6 asserts that exactly one of two
opted-in targets produces a sidecar.

The pinned snapshot is never mutated. Verification copies it to the system
temporary directory — a scratch parent beside the snapshot or inside the working
directory is refused — and compares the original's byte count and SHA-256 before
and after, failing closed on a difference.
`testVerificationLeavesTheSnapshotByteIdentical` and
`testAnInterruptedRunLeavesNoScratchStateAndAnUnchangedSnapshot` assert both.

### What the milestone found about its own tooling

The to-do demo was the milestone's honest test, and it surfaced two defects in
the advisor. Both were fixed inside the milestone, and both are recorded on the
issues that owned them
([#397](https://github.com/lukevanin/swiftql/issues/397#issuecomment-5582478990),
[#398](https://github.com/lukevanin/swiftql/issues/398#issuecomment-5582479277)).

1. **The improvement rule rejected every sort-serving index.** An index walked
   in order constrains no column, and rule v1 required at least one constrained
   column — so it rejected the whole remedy for two of the three diagnosed
   shapes. Three real demo candidates removed a temporary B-tree outright and
   were each rejected for narrowing nothing. Rule **v2** also accepts a
   temporary B-tree the after-plan no longer materializes, and keeps the clause
   that the index SQLite adopted must be the candidate's own. The classifier
   gained `index_scan` beside `index_search` in the same change, because naming
   an ordered index walk a "search" made a sort-serving index look like a
   narrowing one.
2. **A verified recommendation with no diagnostic never reached the build log.**
   The DDL was appended to diagnostic lines, so a recommendation from a
   statement no diagnostic fired on had nowhere to appear — six of the demo's
   nine. Recommendations now carry their own `plan.verified-index` warning line.

The demo's own outcome: nine verified indices applied, every table access now an
index search, and three remaining warnings each recorded with its reason in a
checked-in suppression file. Final state on the demo's build: 0 reported, 3
suppressed, 0 stale suppressions.

### Determinism

The two new artifacts are byte-reproducible, which several of the milestone's
own requirements rest on. Neither retains a timestamp, host identity, process
identity, or path. Records, diagnostics, candidates, and recommendations are all
canonically ordered, and a candidate's representative statement is the
lexicographically first source rather than whichever was discovered first, so
manifest ordering cannot change the output.
`testRepeatedRunsProduceByteIdenticalPlanSidecars`,
`testPlanRecordsAreOrderedByQueryIDRegardlessOfManifestOrder`,
`testCandidateSetsAreIndependentOfManifestOrdering`, and
`testRepeatedVerificationsProduceIdenticalRecommendations` assert it.

Two determinism defects were found in review and fixed inside the milestone: an
unexpected error's description was interpolated into an unsupported reason, and
a filesystem refusal's per-run temporary path was interpolated into an
unverified reason. Both now name the error type unless the error is one this
validator raises and knows to be host-independent.

### Compatibility surface

The Swift 5.9 package floor is unchanged, and so are the iOS 16 / macOS 13
platform floors. `Package.swift` gains one library target, one executable
target, one product pair, and one test target; no existing target's dependencies
changed. The new executable target and its product share a name, for the reason
[#492](https://github.com/lukevanin/swiftql/issues/492) established for
`swiftql-build-validate`.

The demo's `TodoKit` target gains a GRDB dependency, used by exactly one file.
That is a property of the example package, not of SwiftQL, and it exists because
SwiftQL has no index DDL: the advisor can name the index and prove the plan
improves, and the library cannot run the statement. Typed DDL is
[#139](https://github.com/lukevanin/swiftql/issues/139) in v2. The README, the
DocC article, and the file itself all say so.

### Public API changes and deprecations

**Added.** Two products: the `SwiftQLSQLiteIndexAdvisor` library and the
`swiftql-index-advisor` executable. In
`SwiftQLSQLiteBuildValidationValidator`: the plan model, classifier, probe,
report, diagnostics and suppressions, table resolver, predicate extractor,
candidate model and generator, recommendation model, verifier, and scratch
custodian, plus `SQLiteBuildValidationRunResult` and the `run(...)` entry points
beside the existing `validate(...)`. Five CLI options: `--plan-output`,
`--plan-suppressions`, `--plan-scan-row-threshold`,
`--verify-index-candidates`, and, on the advisor, `--plan-report`/`--apply`.

**Changed.** `SQLiteBuildValidationValidatorCLIRunResult` gains an optional
`planReport`; its `exitCode` rule is unchanged.
`SQLiteBuildValidationValidatorCLIOptions` and its nested `Resolved` gain the
new fields, each defaulted, and both now spell out an initializer so a caller
that never mentions plan analysis need not. `SQLiteBuildValidationValidatorCLIError`
gains four cases.

**Removed or deprecated.** Nothing.

No existing signature changed shape, and
`scripts/ci/check-downstream-swift5-client.sh` builds a downstream Swift 5
client against the release tree unchanged.

## Remaining work and disposition

- **[#546](https://github.com/lukevanin/swiftql/issues/546)** — the five
  `#SendableMetatypes` warnings. Pre-existing, tracked in the v2 milestone, not
  a v1.8 regression, and unchanged by this line.
- **[#139](https://github.com/lukevanin/swiftql/issues/139)** — typed DDL. v1.8
  produces index statements that SwiftQL itself cannot express. This is the
  clearest motivation the issue has had, and it is recorded on the demo and in
  the release notes rather than deferred silently.
- **Nested remediation.** Candidate generation considers root plan nodes only. A
  scan inside a subquery needs that subquery's own `FROM` scope, which the
  extractor does not track. Scoped out deliberately, and stated in the
  architecture record.
- **Schema-only snapshots.** A write-cost note reads "0 rows at verification
  time" against a snapshot that carries no data, and the scan diagnostic's row
  threshold never fires there. The advisor measures the snapshot it is given;
  recommendations and their evidence are unaffected, because they rest on plan
  shape rather than on row counts.
