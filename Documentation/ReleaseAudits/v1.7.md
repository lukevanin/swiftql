# SwiftQL v1.7 release-readiness audit

The v1.7 line — "the `REGEXP` operator, made to work" — is a single-milestone
minor release. Milestone
[v1.7](https://github.com/lukevanin/swiftql/milestone/18) holds the whole line,
so this record is produced at the `v1.7.0` release, as `RELEASING.md` requires
for every `vX.Y.0`. It is an evidence-backed record rather than an
implementation task, and it does not weaken, skip, or relabel any validation to
reach a verdict.

Audited commit: `8c92a7a7` on `version/1.7`, the merge of
[#623](https://github.com/lukevanin/swiftql/pull/623) and the last content
commit of the milestone. Every result below was produced against that exact
commit. This record is written on the release-preparation change that sits
directly on top of it, which adds only the documentation and release artifacts
listed under "Documentation currency", plus one fix to a CI script described
under "One check repaired"; the preparation change is re-validated in its own
pull request rather than re-audited here.

## Verdict

**Ready for `v1.7.0`**, subject to the human-gated release process in
`RELEASING.md`. No product, documentation, compatibility, packaging, security,
or performance blocker remains. Every issue retained in the milestone is
delivered by a merged pull request, the full first-party suite passes on the
audited tree, and the documentation, compatibility, and conformance records
agree with what the milestone shipped.

One local check fails, and it is the same pre-existing, already-tracked failure
the v1.5 and v1.6 audits recorded: `check-strict-concurrency.sh` reports five
first-party `#SendableMetatypes` warnings, tracked as
[#546](https://github.com/lukevanin/swiftql/issues/546) in the v2 milestone. It
is not a v1.7 regression; the warning set and the files are unchanged.

Three things belong to the release preparation itself rather than to this audit
and are listed under "Release-preparation actions": the milestone is still open
and must close as `RELEASING.md` step 1 requires, the changelog heading is still
`Unreleased`, and the seven-cell compiler matrix has not yet run on `main` with
this content.

### What the operator now does, and what it costs

`X REGEXP Y` has rendered since v1.4.2. SQLite parses it as `regexp(Y, X)` and
ships no such function, so before this release the statement rendered correct
SQL and then failed to prepare with `no such function: regexp` unless the
application registered one itself. The rendered SQL is unchanged by this
release; only the registration is new.

Shipping the function means defining what a pattern means, because SQLite
defines no regular-expression dialect. The decisions, each covered by evidence
in the conformance inventory:

| Case | Behaviour |
| --- | --- |
| Pattern syntax | Swift's, as accepted by `Regex.init(_:)` |
| Match rule | The pattern is searched for anywhere in the subject, matching the widely used SQLite `regexp` extensions and PostgreSQL's `~` |
| `NULL` on either side | `NULL` |
| Invalid pattern | `XLRegexpFunctionError.invalidPattern`, naming the pattern |
| An argument that is neither TEXT nor a UTF-8 BLOB | `XLColumnReadError`, rather than a silent conversion |
| A `regexp` the application already registered | Kept; SwiftQL never replaces it |

The precedence rule is matched on the function name and on either the exact
argument count or the `-1` SQLite reports for a variadic function, and it costs
one `PRAGMA function_list` per database rather than one per query. It is proven
for a function registered through `GRDBDatabaseBuilder.addFunction(_:)` and for
one registered through `Configuration.prepareDatabase(_:)`.

Two limits are deliberate and are documented rather than hidden. The
`XLRegexPattern` registry does not keep a pattern alive, so a released pattern
raises `XLRegexpFunctionError.unregisteredPattern` rather than matching nothing;
and a statement carrying an `XLRegexPattern` key cannot become a static query
descriptor, because a key names a registration in one process while a
descriptor's identity has to be reproducible. A pattern string carries no such
limit and passes the build validator.

### One check repaired

`scripts/ci/check-core-contract-boundary.py` builds `SwiftQLCore` in a
generated, dependency-free package to prove the module reaches neither GRDB nor
CSQLite. That generated manifest declared no `platforms`, so it defaulted to
macOS 10.13. v1.7 is the first release to put `Regex`, which is macOS 13 or
newer, into `SwiftQLCore`, so the isolated build began failing on macOS with
availability errors while continuing to pass in CI, where the job runs on
`ubuntu-latest` and the annotation does not apply.

The preparation change adds `platforms: [.iOS(.v16), .macOS(.v13)]` to that
manifest, mirroring the real `Package.swift` floor. The check's subject is the
module boundary, and the fix restores its meaning on macOS without weakening
it: the boundary assertions and the GRDB/CSQLite artifact scan are unchanged,
and the check passes on both platforms. This is a defect in the check rather
than in the shipped code, and it was never a false pass — the isolated build
had simply never compiled anything platform-gated before.

### Performance

The pattern cache is the release's one performance claim, and it is an exact
one: `XLRegexpPatternCacheTests.testOnePatternIsCompiledOncePerStatementExecution`
asserts the compile count, not a duration. SQLite calls a scalar function once
per candidate row and passes the pattern again on each call, so an
implementation without the cache compiles the pattern once per row.

`XLRegexpPatternCacheTests.testRecordsTheScanImprovement` records the wall-clock
effect alongside the exact count, the way the render-once benchmark in the same
suite does. On the audited tree, over a 2000-row scan against `^row-1[0-9]$`:
one compile instead of 2000, 0.0009 s against 0.0417 s, a 47.2x wall-clock
ratio. The ratio is noisy and corroborating only; the compile count is the
assertion.

The cache holds at most 16 compiled patterns, caches a compile failure so an
invalid pattern is not recompiled per row, and belongs to one registered
function on one connection. It is never shared between connections, because
Swift's `Regex` is not `Sendable` and pooled connections match concurrently.

### Compatibility surface

No new source-level API difference across compiler cells. The two recorded in
`COMPATIBILITY.md` are unchanged: `#row`'s two-to-six column shapes require
Swift 6.1 or later, and `sql { ... }` as a subquery requires Swift 6.1 or later.

`Regex` requires iOS 16 or macOS 13, which is exactly SwiftQL's existing
platform floor, so the `REGEXP` surface adds no platform requirement. It needs
no particular SQLite version either: the operator has been in SQLite's grammar
since 3.0.0, and the missing piece was always the function rather than the
parser.

`COMPATIBILITY.md` gained one unrelated correction during the line: the
inline-statement `swift-frontend` segfault is now recorded for the pinned Swift
5.9.2 toolchain as well as the pinned Swift 6.0 cell.

### Public API changes and deprecations

Additive. **No deprecations, no removals, and no renames.** Added:

- `XLRegexpFunction`, the bundled implementation, and `XLRegexpFunctionError`
  with its `invalidPattern` and `unregisteredPattern` cases.
- `XLRegexPattern`, a `RegexBuilder`-built pattern usable as the right operand
  of `REGEXP`, and `XLRegexPatternRegistry` behind it.
- `XLExpression.regexp(_:)` overloads taking an `XLRegexPattern`, for `String`
  and `Optional<String>` subjects. The existing string overloads are unchanged.
- `XLRegexpMatcher` and `XLRegexpPatternCache`, the matcher and its bounded
  cache.
- `XLCustomFunctionDefinition`, the deterministic function signature a static
  query descriptor records, and `XLStaticStatementDefinitionError`.

`XLCustomFunctionDefinition`, `XLRegexpFunctionError`, and the matcher moved
from `SwiftQL` to `SwiftQLCore`. Nothing is renamed, and `SwiftQL` re-exports
`SwiftQLCore`, so `import SwiftQL` is unaffected. The move is what lets the
build validator, which does not depend on the GRDB adapter, register the same
implementation the adapter registers.

The one behavioural change a reader should notice is that a query using
`REGEXP` now prepares where it previously threw. Code that depended on that
failure is the only code this release changes.

## Release-preparation actions

Owned by the release process rather than by this audit, and to be completed in
`RELEASING.md` order:

1. Close milestone [v1.7](https://github.com/lukevanin/swiftql/milestone/18)
   with no open issues, and verify it against the live API as step 1 requires.
2. Merge `version/1.7` into `main` with a merge commit, and confirm the
   seven-cell `Swift compatibility` matrix and `Documentation` both pass on
   `main` with this content.
3. Run `scripts/ci/test-release-workflow.sh`, then the three safe test tags,
   while the changelog heading still says `Unreleased`.
4. Date the heading to `## [1.7.0] - YYYY-MM-DD`, move the pin in
   `SQLDocumentationCatalogTests`, and align the `WHATSNEW.md` and blog dates.
5. Verify immutable releases and the `Protect v-prefixed release tags` ruleset
   out of band, record `$release_sha`, tag, and publish.
6. Post the tag-run, release, asset, attestation, and ruleset evidence in the
   dedicated v1.7.0 release issue, then announce: v1.7 is a minor release, so it
   is announced rather than shipped silently.
