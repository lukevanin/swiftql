# SwiftQL v1.4 release-readiness audit

The v1.4 line — "Common SQLite feature coverage" — was delivered across the
`v1.4.1`–`v1.4.6` patch milestones. Its closeout audit,
[#229](https://github.com/lukevanin/swiftql/issues/229), is scheduled in the
final `v1.4.6` milestone, so this single checked-in record covers the line and
is produced at the `v1.4.6` release (`v1.4.1`–`v1.4.5` produced none, as
`RELEASING.md` states). It is an evidence-backed record, not an implementation
task, and it does not weaken, skip, or relabel any validation to reach a
verdict.

## Verdict

**Ready for `v1.4.6` and v1.4-line closure.** The v1.4 feature surface is
delivered against real SQLite with consistent documentation, the `v1.4.6`
hardening work is merged and validated, and every planning discrepancy the audit
found has been reconciled or tracked. The one item that did not meet its
original goal — #266's decode-latency recovery — is delivered as an
evidence-backed allocation reduction with the remaining latency owned by
follow-up [#353](https://github.com/lukevanin/swiftql/issues/353), and #266 is
closed as an accepted partial.

## Verified facts

### v1.4 feature line

The v1.4 line added a documented, real-SQLite-proven common-SQLite subset across
its patch releases: expanded comparison/membership/range/pattern operators
(`IN`/`NOT IN`, `BETWEEN`, `LIKE ESCAPE`, `REGEXP`/`GLOB`), custom collations,
aggregates, `CAST`, typed date-and-time functions (`v1.4.3`),
`INSERT OR` conflict resolution (`v1.4.4`), and, in `v1.4.5`, the join surface
(`NATURAL`/`USING`, `RIGHT`, `FULL OUTER`, `CROSS`), `MATERIALIZED` common
tables, and direct scalar CTE rows (#43) that remove the one-column
`SQLScalarResult` wrapper requirement. SwiftQL still documents this as a
supported subset, not complete SQLite grammar coverage.

#### #166 — construction/rendering overhead

Delivered. A checked-in deterministic allocation profiler
(`swiftql-construction-profile`, `malloc_logger`-based) attributed ~77% of the
`swiftql_construction_and_rendering` phase's allocations to rendering. Three
output-preserving builder changes (single-argument token append, a single-token
`build()` fast path, and a one/two-component `scopedName` fast path) cut render
allocations ~15% and the phase median ~13-17% across the #128 harness read
cases, with byte-identical SQL. Evidence:
[`Benchmarks/Profiling/Issue166`](../../Benchmarks/Profiling/Issue166/README.md).
No rendered SQL, entity metadata, public 1.x API, or Swift 5.9 support changed;
no absolute CI latency gate was added.

#### #266 — incremental-decode latency (partial)

The incremental cursor path now reuses one per-row normalization buffer instead
of allocating a fresh `[XLSQLiteValue]` (plus a redundant `Array` copy) per row,
preserving the #248 bounded-memory guarantee (the typed decode path materializes
no intermediate matrix). A before/after on the exact 16,143-row #250 fixture
measured 76.08 ms → 76.22 ms (+0.2%, inside the 0.3% base spread) with peak RSS
~37 MiB preserved — a genuine null result showing the regression is
decode-compute bound, not allocation bound (the harness's `grdb_manual` control
does the same fetch in ~6.9 ms). Evidence:
[`Benchmarks/Comparison/Issue266`](../../Benchmarks/Comparison/Issue266/README.md).
The remaining latency work is scoped atomically in #353.

#### #227 / #228 — documentation and agent guidance

The v1.4 documentation reconciliation these issues asked for was completed by the
v1.4.5 documentation state on `main`: the conformance counts, README, DocC,
`COMPATIBILITY.md`, and `SKILL.md` already describe the current
111/104/164 inventory consistently, superseding the earlier 106/98/144
reconciliation prepared on the `version/1.4.6` branch. Those superseded
count edits were intentionally not re-applied in this release. The documentation
regression contract (required-phrase, README-link, file-header, README-example,
and skill suites) passes on the release commit.

### SQLite conformance inventory

The canonical inventory records **111 feature records** (104 supported, 0
partial, capability-gated/intentionally-unsupported/unimplemented as recorded)
and **164 evidence records** (101 exercising real SQLite against SQLite 3.51.0).
README, `COMPATIBILITY.md`, `CHANGELOG.md`, `Conformance/SQLite/REPORT.md`, and
`SKILL.md` state these counts consistently; the documentation-catalog and skill
regression tests recompute them from the JSON.
