## Fewer crashes, fewer silent wrong answers

SwiftQL 1.8.1 is a correctness and safety patch: code that stopped the process,
returned a silently wrong result, or ran an unbounded match now either works or
throws a typed error you can handle.

A `REGEXP` or custom-function query inside a result set inside a transaction no
longer crashes, because functions are installed once per connection rather than
before every execution, and a static row layout now works at every select and
`RETURNING` entry point. Nested queries built from the enclosing schema keep their own aliases and
bindings, a
nested request no longer resets the cursor around it, and text containing a NUL
character is refused instead of being stored truncated. `REGEXP` bounds the
length of its pattern and subject, so a pattern typed into a search field
cannot pin a connection, and live-query streams no longer need the main thread.

Some of those fixes are visible in source. A compound branch may no longer
carry its own `LIMIT`, which SQLite silently applied to the whole compound:

```swift
// 1.8.0: ran, with LIMIT applied to the whole compound.
// 1.8.1: throws XLSQLValueEncodingError.unsupportedCompoundBranchClause.
select(seed).unionAll { select(step).from(this).limit(10) }

// Both versions: the same SQL, written where it applies.
select(seed).unionAll { select(step).from(this) }.limit(10)
```

**Upgrade impact.** This patch can require changes to code that ran on 1.8.0:

- `XLSQLValueEncodingError` gains `contextualOnlyValueInLegacyWrite`,
  `nulCharacterInText`, and `unsupportedCompoundBranchClause`, and
  `SQLiteIndexAdvisorError` gains `forceRequiresApply`,
  `outputConflictsWithPlanReport`, and `outputNotGenerated`. A `switch` without
  `default` must add them.
- A `REGEXP` pattern longer than 1,024 UTF-8 bytes, or a subject longer than
  16,384 UTF-8 bytes, fails with `XLRegexpLengthLimitError`.
- `QueryBuilder` folds `and` and `or` in call order, which changes the rendered
  `WHERE` clause of a query that mixes them.
- A compound select whose right-hand branch has `WITH`, `ORDER BY`, `LIMIT`, or
  `OFFSET`, or is itself a compound, is rejected. A recursive common table with
  `.limit(n)` inside its `unionAll` closure now throws; write
  `.unionAll { ... }.limit(n)`.
- Text that contains U+0000 is rejected, as a literal and as a bound value.
- Automatic aliases for unnamed nested sources change, an inner automatic
  binding gets its own name, and two unrelated automatic bindings that render
  the same name fail with `conflictingParameterKey`.
- Functions are installed once per connection: two `XLCustomFunction` types
  with one name and argument count share the first installed implementation,
  SwiftQL's marker functions appear in `PRAGMA function_list`, and replacing a
  bundled function while a statement is active throws instead of crashing.
- `stream()` and `streamOne()` deliver on a private queue, not the main queue.
- The build validator fails a run whose snapshot changes during index
  verification, and `swiftql-index-advisor --apply` refuses to overwrite a file
  without its generated header unless given `--force`.

No platform or compiler requirement changes. One known gap remains: a custom
`XLRowReadable` that is not a static layout, and whose `readRow` throws, still
traps in `Select.init(_:)` and `Returning.init(_:)`; the fix needs a
source-breaking change and is tracked for v2.0 as
[#744](https://github.com/lukevanin/swiftql/issues/744).

Full detail, with a migration step for each change, in the
[changelog](../../CHANGELOG.md).
