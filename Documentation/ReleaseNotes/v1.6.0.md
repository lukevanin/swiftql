## SQLite's JSON functions, as typed Swift expressions

A query can now reach inside a JSON document instead of loading the text,
decoding it in Swift, and writing the whole thing back. The `->` and `->>`
selection operators, `json_extract`, the constructor and inspection functions,
the five mutation functions, the two aggregates, and all of their JSONB
variants are typed SwiftQL expressions. Nothing here is a raw-SQL escape hatch:
a path is a text operand and a written value is a bound parameter, like every
other operand in the library.

Paths are built from segments rather than written as strings, so a key that
contains a `.` names that key instead of changing the shape of the path:

```swift
let priority = XLJSONPath.root.key("priority")

let urgent = sql { schema in
    let note = schema.table(Note.self)
    Select(note)
    From(note)
    Where(note.metadata.jsonValue(at: priority, as: Int.self) > 3)
}
```

Decoding got substantially faster in the same release. A literal column now
selects a statically-constrained read instead of resolving its conformance at
run time, and the generated row closure builds each column's expression once
rather than once per row. On a 16,143-row, 14-column fetch the two changes
measured 39.4% and a further 28.3%, which compose to about 56%. No source
change is needed to get it: existing `@SQLTable` and `@SQLResult` models reach
the faster path as they are.

**Upgrade impact.** The JSON surface is additive. `validJSON()` is deprecated in
favour of `validJSONOrNull()`, because `json_valid(NULL)` returns SQL `NULL`
rather than false and a non-optional `Bool` cannot represent that; the old
spelling still compiles and renders the same SQL. An `XLRowReader` conformance
outside this package that overrides the unconstrained `staticColumn(_:alias:)`
to give literal columns behaviour `column(_:alias:)` does not give must
implement the new constrained requirement as well to keep it; a reader that
implements only `column(_:alias:)` is unaffected. Parts of the JSON surface
need a newer SQLite than SwiftQL's oldest supported engine — 3.38.0 for the two
operators, 3.45.0 for JSONB and for `json_valid` with flags, and 3.46.0 for
`json_pretty` — and SwiftQL renders the SQL either way. Using `sql { ... }` as
a subquery requires Swift 6.1 or later, recorded in
[COMPATIBILITY.md](../../COMPATIBILITY.md#swift-59-and-swift-60-api-surface-gaps).
