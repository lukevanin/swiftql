## A declared query is now the whole read path

SwiftQL has had declared queries since v1.5. You write a Swift method and give
its body a statement builder. SwiftQL renders the SQL once and binds the
parameters for you. A declaration could only fetch. A view that observed the
same read kept a second copy of the statement. A read inside a transaction
opened a transaction of its own. A search that matched text with `LIKE` or
`REGEXP` could not be declared at all. This release removes all three limits.

Each declaration now has a prepared form. `stream()`, `publish()`, and the
`@Observable` wrappers accept it. A view thus observes the request and the
bindings that the executor already uses. A declaration called on the scope that
`withTransaction(_:)` gives its body runs on that transaction and reads its
uncommitted writes. A parameter now becomes a named binding when you pass it to
a DSL method or clause. `column.regexp(pattern)` and `Limit(count)` are two
examples. Before, that gave an error which said the value would be frozen into
the SQL.

The macros also lower each declaration to a static descriptor. A new build-tool
plugin reads every declaration in a target and generates a registry.
`SQLiteBuildValidationDeclaredQueryManifest.makeManifest(...)` turns that
registry into a build-validation manifest. A hand-written manifest is now the
fallback. Two limits apply to that path. The registry plugin runs only in a
SwiftPM target, not in an Xcode target (issue #766). Only `SELECT`-shaped
declarations exist, so a write still goes into the manifest by hand. The
validation plugin itself now also runs in an Xcode application target.

```swift
@SQLQueries
extension GRDBDatabase {

    private struct Query {
        func todos(listID: TodoUUID, pattern: String) -> [Todo] {
            sqlResult { schema in
                let todo = schema.table(Todo.self)
                Select(todo)
                From(todo)
                Where(todo.listID == listID && todo.title.regexp(pattern))
            }
        }
    }
}

// Fetch, as before. `list` is a row the caller already holds.
let rows = try database.todos(listID: list.id, pattern: "urgent")

// Observe the same declaration. One render, one set of bindings.
let query = try database.preparedQueries.todos(listID: list.id, pattern: "urgent")
for try await todos in query.stream() {
    print("\(todos.count) matching rows")
}
```

The same executor runs on a transaction scope. Call
`scope.todos(listID:pattern:)` inside a `withTransaction(_:)` body, and it reads
the writes that the body made before it.

Two more changes touch code that is not a declared query. The new
`@SQLBindings` macro generates a typed packet for the named bindings of a
statement. A misspelled binding name is now a compile error instead of a runtime
failure. `GRDBDatabase.insert(contentsOf:)` renders and prepares one insert for
a whole batch. On the Issue259 `transactional_write` workload, it cut the median
of a 100-row transaction from 993.42 us to 363.98 us.

**Upgrade impact.** This release is not purely additive. Check for these:

- **A name collision with a generated member.** The macros generate
  `preparedQueries` and `declaredQueries` on a `@SQLQueries` type. They also
  generate a `<name>PreparedQuery` peer and a `<name>DeclaredQuery` peer beside
  each `@SQLQuery` declaration. Rename your member or your specification.
- **A `Data` value passed to a JSON function.** It now throws
  `blobInJSONValue`. Pass it through `minifiedJSONB()`, or leave it out of the
  document.
- **A JSON mutation on a `NOT NULL` document.** The result is non-optional now.
  Code that unwraps that result twice must unwrap it once.
- **`jsonRemoving` or `jsonbRemoving` on the root path `$`.** The call now
  throws `jsonRootRemoval`. On 1.8.1 it returned SQL `NULL`.
- **A `Bool` written into JSON.** It is now JSON `true` or `false`, not `1` or
  `0`. A reader that reads such a member as a number must change.
- **A `switch` over `XLSQLValueEncodingError` with no `default` clause.** It
  must handle `blobInJSONValue` and `jsonRootRemoval`.
- **The build-validation manifest.** It writes format version 2, which makes
  several properties optional. The reader still accepts version 1.
  `SQLiteBuildValidationManifestFormatVersion.current` is now `.v2`. Pass
  `formatVersion: .v1` to keep writing version 1.
- **An unknown key in the manifest or in `swiftql-plan-analysis.json`.** The
  read now fails with `unknownKey(path:)`. `SQLiteBuildValidationManifestError`
  and `SQLiteBuildValidationPlanSuppressionError` each gain that case, so a
  `switch` with no `default` clause must handle it.
