## A declared query is now the whole read path

SwiftQL has had declared queries since v1.5: a Swift method whose body is a
statement builder, whose SQL renders once, and whose parameters SwiftQL binds
for you. A declaration could only fetch. A view that observed the same read
kept a second copy of the statement, a read inside a transaction opened a
transaction of its own, and a search that matched text with `LIKE` or `REGEXP`
could not be declared at all. This release removes all three limits.

Each declaration now has a prepared form that `stream()`, `publish()`, and the
`@Observable` wrappers accept, so a view observes the request and the bindings
that the executor already uses. A declaration called on the scope that
`withTransaction(_:)` gives its body runs on that transaction and reads its
uncommitted writes. A parameter that you pass to a DSL method or clause, such
as `column.regexp(pattern)` or `Limit(count)`, becomes a named binding instead
of a frozen-literal error. The macros also lower each declaration to a static
descriptor, and a new build-tool plugin reads every declaration in a target and
generates the build-validation manifest from it, so a hand-written manifest is
now the fallback.

```swift
@SQLQueries
extension GRDBDatabase {

    private struct Query {
        func todos(listID: TodoUUID, pattern: String) -> [Todo] {
            sqlResult { schema in
                let todo = schema.table(Todo.self)
                Select(todo)
                From(todo)
                Where(todo.listID == listID && todo.title.regexp(pattern))
            }
        }
    }
}

// Fetch, as before.
let rows = try database.todos(listID: listID, pattern: "urgent")

// Fetch on a transaction, and read what the body wrote.
try database.withTransaction { scope in
    try scope.makeRequest(with: sqlInsert(todo)).execute()
    return try scope.todos(listID: listID, pattern: "urgent")
}

// Observe. The same cache entry, the same bindings, one render.
let query = try database.preparedQueries.todos(listID: listID, pattern: "urgent")
for try await rows in query.stream() {
    print("\(rows.count) matching rows")
}
```

Two more changes touch code that is not a declared query. The new
`@SQLBindings` macro generates a typed packet for the named bindings of a
statement, so a misspelled binding name is a compile error instead of a runtime
failure. `GRDBDatabase.insert(contentsOf:)` renders and prepares one insert for
a whole batch, and cut the median of a 100-row transaction from 993.42 us to
363.98 us on the Issue259 `transactional_write` workload.

**Upgrade impact.** The macros generate new members, and a member with one of
these names stops compiling: `preparedQueries` and `declaredQueries` on a
`@SQLQueries` type, and a `<name>PreparedQuery` or `<name>DeclaredQuery` peer
for each `@SQLQuery` declaration. Rename your member or your specification.
Three JSON changes can alter source or behaviour: a `Data` value passed to a
JSON function now throws `blobInJSONValue`, so pass it through
`minifiedJSONB()`; a mutation on a `NOT NULL` document has a non-optional
result, so code that unwraps it twice must unwrap it once; and a `Bool` is
written as JSON `true` or `false` instead of `1` or `0`, so a reader that reads
it as a number must change. A `switch` over `XLSQLValueEncodingError` with no
`default` clause must handle `blobInJSONValue` and `jsonRootRemoval`. The
build-validation manifest writes format version 2, which makes several
properties optional and rejects an unknown key, and the reader still accepts
version 1.
