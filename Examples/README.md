# SwiftQL examples

A classic Xcode playground that runs SwiftQL against a real SQLite database,
plus the compiled module it imports.

## Opening it

1. Open `Examples/SwiftQLExamples.xcworkspace`. The workspace contains the
   SwiftQL package and the playground, which is what lets the playground see
   the package's compiled modules.
2. Wait for package resolution to finish.
3. Choose the **SwiftQLExamples** scheme and **My Mac** as the destination,
   then build (⌘B).
4. Open `GettingStarted.playground` and run a page.

Step 3 matters. A playground imports modules that the workspace's active
scheme has already built for the playground's platform, so selecting a scheme
that does not build `SwiftQLExamples` for macOS gives you "no such module
'SwiftQLExamples'" on the import line. The playground sets
`buildActiveScheme='true'`, so Xcode rebuilds the active scheme before each
run once the scheme is right.

The schemes here are Xcode's auto-generated ones. SwiftQL's `.gitignore`
excludes `/.swiftpm`, where a shared package scheme would have to live, so
there is no checked-in scheme to select instead.

## Why the schema lives in a compiled module

SwiftQL's public API is macros: `@SQLTable` declares a table, `@SQLQuery`
declares a query. Expanding a macro needs a compiler plugin, which SwiftPM
builds and passes to the compiler. A classic playground has no `Package.swift`
and no reliable way to load that plugin, so a page that writes `@SQLTable`
cannot be counted on to compile.

`Examples/Sources/SwiftQLExamples` is an ordinary target of the SwiftQL
package, declared in the repository-root `Package.swift`. Its macros expand
during the normal package build, and what the playground imports is
already-expanded, already-compiled Swift:

- `Person` and `Occupation`, declared with `@SQLTable` in `ExampleSchema.swift`.
- `fetchPeopleNamed(name:)` and `fetchPersonByID(id:)`, generated by
  `@SQLQuery` from the specifications in `ExampleQueries.swift`.
- `ExampleDatabase`, which creates a throwaway SQLite file with the schema
  already in place, optionally seeded with a fixed set of rows.

Everything else stays in the playground, because it needs no macro.
`sql { }` is a function taking a result builder, and `sqlCreate`, `sqlInsert`,
`makeRequest(with:)`, `fetchAll()`, and `stream()` are ordinary functions and
methods, so a page can write a query, run it, and show the result inline.

`ExampleQueries.swift` uses `@SQLQuery` rather than the `@SQLQueries`
container form that
[Declared queries](../Sources/SwiftQL/SwiftQL.docc/DeclaredQueries.md)
recommends for product code.
`@SQLQueries` copies its extension's access level onto every member it
generates, so the `public extension` needed to reach the executors from the
playground expands to `public func` members inside an already-public
extension, and the compiler warns that the modifier is redundant. SwiftQL
builds first-party targets with warnings as errors, so that expansion cannot
ship. `@SQLQuery` takes its modifiers from the specification function, which
carries the access level without the redundancy.

## Keeping it working

`SwiftQLExamples` is a first-party target, so `swift build` and the CI warning
gate compile it on every run, and an API change that breaks the example schema
breaks the build. The playground pages themselves are not compiled by
`swift test`, so opening the workspace and running each page is still a manual
check.
